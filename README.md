## 一、專案簡介

**台中城市模擬器（Taichung City Simulator）** 是一個以台中城市生活與交通運輸為靈感所開發的網頁模擬專案。

本專案希望將城市道路、公共運輸、車輛移動與互動式介面結合，讓使用者能透過瀏覽器探索模擬器的各項功能，並逐步體驗一個持續擴充的虛擬城市。

與需要下載大型遊戲、安裝遊戲引擎或建立複雜執行環境的傳統遊戲不同，本專案以網頁為主要遊玩入口。使用者可以直接開啟 GitHub Pages 上的版本頁面，依照各版本提供的功能進行操作。

本專案的開發方向不只是製作一個可以顯示車輛的畫面，而是希望建立一個可以不斷成長的城市模擬平台。

從公車路線、交通控制、城市移動，到未來可能加入的行人、交通號誌、更多道路與城市設施，每個功能都可以成為後續開發的重要部分。

### 1.2 專案的核心方向

台中城市模擬器主要圍繞以下幾個方向發展：

- **城市模擬：** 建立具有城市氛圍的虛擬環境。
- **公共運輸：** 以台中公車路線為靈感，提供路線選擇與交通互動介面。
- **交通控制：** 透過方向按鈕、暫停功能及其他控制項目進行操作。
- **多版本體驗：** 保留不同開發階段的版本，方便比較與測試。
- **網頁化遊玩：** 盡可能降低開始體驗的門檻。
- **持續擴充：** 為更多車輛、道路、行人、捷運及城市事件預留發展方向。

### 1.3 這是一個怎樣的城市模擬器？

可以把本專案想像成一個正在逐步建設的虛擬台中。

使用者可以從現有版本開始，查看交通控制介面與可用的路線選項。隨著程式持續更新，開發者也可以加入新的交通工具、互動方式、城市區域與模擬機制。

本專案重視的不只是畫面呈現，也包含功能設計、操作體驗、程式維護與未來擴充的可能性。

需要注意的是，本專案的名稱與設計靈感來自台中，但不代表目前已經完整還原台中所有行政區、道路、建築、交通班次或即時交通狀況。實際內容應以各版本目前實作的功能為準。

## 二、專案目標與開發理念

### 2.1 為什麼要製作台中城市模擬器？

城市本身就是一個複雜的系統。

道路連接不同地區，公車將乘客從一個地方送往另一個地方，行人透過人行空間移動，交通號誌影響車輛通行，而捷運與其他大眾運輸工具則負責連接更多城市區域。

這些元素共同構成日常生活中的交通網路。

台中城市模擬器希望將這些概念轉化成容易接觸的網頁體驗，讓使用者可以透過互動方式理解城市交通的組成。

本專案也提供一個實際的網頁開發練習方向：從簡單的按鈕與畫面開始，再逐步思考狀態管理、車輛移動、路線資料、互動事件與效能最佳化。

### 2.2 開發原則

#### 原則一：操作直覺

遊戲介面應該讓使用者容易理解。

例如，方向按鈕可以用於移動控制，暫停按鈕可以用於控制模擬狀態，而路線按鈕則可用於選擇不同交通路線。

未來新增功能時，也應盡量使用清楚的名稱、圖示與提示，避免讓新使用者必須閱讀大量文件才能開始操作。

#### 原則二：版本清楚

每個公開版本都應具有獨立入口。

不同版本可能有不同的功能、介面、路線或實驗性設計，因此應保留版本之間的區別，而不是直接刪除所有舊版。

版本清楚有助於開發者比較變更，也方便使用者回報問題時提供準確的版本資訊。

#### 原則三：逐步擴充

不需要在第一個版本就完成所有功能。

可以先完成基本的交通控制，再逐步加入更多路線、車輛、行人、交通規則與城市設施。

每次更新都應盡可能確保既有功能不會因為新功能加入而失效。

#### 原則四：維持網頁的可用性

網頁應盡可能適用於常見的桌面瀏覽器。

如果未來加入大量動畫、車輛或複雜模擬運算，也應注意效能，避免不必要的畫面更新與重複運算。

#### 原則五：以實際測試為準

介面上出現某個按鈕，不代表它背後的功能一定已經完整實作。

因此，開發文件應清楚區分已確認的介面、已驗證的功能，以及仍在規劃中的項目。

這樣能讓使用者了解專案目前的狀態，也能避免對功能產生錯誤期待。

### 5.1 城市模擬系統

城市模擬系統是整個專案的核心概念。

未來的城市環境可以包含道路、建築、車站、路口、交通設施與其他城市元素。

這些元素可以用來建立具有空間感的模擬場景，讓使用者不只是操作單一按鈕，而是能理解車輛與城市環境之間的關係。

城市模擬系統可以逐步加入：

1. 道路網路。
2. 車輛移動路徑。
3. 站點與地點資訊。
4. 城市區域切換。
5. 交通狀態顯示。
6. 不同時間的場景變化。
7. 城市環境設定。

在設計這些系統時，應盡可能將地圖資料、交通資料與畫面呈現分開管理。

這樣未來要更換地圖或新增區域時，就不必重新撰寫整個模擬器。

### 5.2 車輛控制系統

目前各版本的介面中可以觀察到方向控制按鈕。

這些控制項目可以作為車輛控制功能的入口。

理想的車輛控制系統可以包含：

- 前進與後退。
- 左右轉向。
- 停止與暫停。
- 車速調整。
- 車輛方向顯示。
- 車輛狀態資訊。
- 路線跟隨模式。
- 手動控制與自動控制的切換。

實際可使用的功能應以各版本的程式實作為準。

未來如果加入更完整的車輛物理系統，可以考慮處理加速度、煞車距離、轉彎半徑與道路邊界。

不過，車輛控制的第一個目標應該是穩定與直覺，而不是一開始就加入過度複雜的物理運算。

### 5.3 公車模擬系統

公車是本專案的重要主題之一。

目前多個版本已經呈現公車圖示，以及不同路線的選擇介面。

未來可以逐步擴充以下項目：

- 公車路線管理。
- 車輛外觀與識別。
- 站點順序。
- 車輛行駛方向。
- 站牌停靠。
- 上下車人數。
- 車輛狀態資訊。
- 車輛數量管理。
- 路線切換。
- 自動駕駛模式。

這些功能可以分開開發，避免在單一系統中混合過多邏輯。

例如，路線管理負責保存站點順序；車輛控制負責決定車輛如何移動；乘客系統則負責管理乘客的上下車狀態。

這種分工能讓程式更容易維護，也方便日後新增更多公車路線。

### 5.4 自動駕駛與機器人

目前頁面中可以觀察到機器人相關圖示。

這個介面元素可以作為未來自動駕駛或自動化交通功能的發展入口。

如果要進一步實作自動駕駛，建議分成幾個階段：

第一階段：讓車輛沿著預先設定的路線移動。

第二階段：讓車輛在指定站點停靠。

第三階段：加入轉彎、停車與路口判斷。

第四階段：加入其他車輛的距離判斷與基本避讓。

第五階段：建立可以調整速度、路線與駕駛行為的設定面板。

第六階段：在不同交通狀況下進行測試，確認車輛不會偏離道路或卡在無法前進的位置。

自動駕駛的開發應以可預測、可測試與可控制為原則。

若未來需要調整車速上限，應將其作為可配置的參數，而不是在程式不同位置重複寫入固定數值。

### 5.5 行人與乘客系統

Beta V1.0.1 的頁面中可以觀察到行人相關圖示。

行人系統是城市模擬的重要延伸方向。

未來可以考慮加入：

- 行人生成。
- 行人路徑。
- 行人移動動畫。
- 行人與站牌的互動。
- 乘客等待公車。
- 乘客上下車。
- 站點人流顯示。
- 行人與車輛的基本安全距離。

乘客系統也可以進一步與公車路線結合。

例如，在模擬場景中設定不同站點的乘客需求，讓部分站點有較多乘客等待，其他站點則只有少量乘客。

這可以讓城市交通不再只是車輛單獨移動，而是逐步形成具有互動性的交通場景。

不過，行人與乘客數量不應無限制增加。若每一位行人都需要獨立更新位置、計算碰撞與搜尋路徑，可能會增加瀏覽器的運算負擔。

因此，未來可透過合理的更新頻率、距離判斷與簡化的路徑演算法改善效能。

### 5.6 捷運系統

Beta V1.0.1 的頁面中可以觀察到捷運相關圖示。

這為未來發展多種公共運輸工具提供了延伸方向。

捷運系統可以規劃以下功能：

- 列車停站。
- 車站轉乘資訊。
- 乘客候車。
- 路線顏色與識別。
- 不同運輸工具之間的轉乘。

如果未來要加入台中捷運的相關場景，建議將實際交通資料與模擬資料分開保存。

真實資料可以用來參考路線名稱與站點資訊，而模擬器則可以依照遊戲需要調整列車速度、發車間隔與乘客行為。

若要呈現真實地理資訊，應另外確認資料來源、更新日期與使用授權。

### 5.7 廣播與交通資訊

目前介面可以看到廣播相關圖示。

未來可將廣播功能設計成模擬器的資訊系統。

例如：

- 車輛到站提示。

### 5.8 交通狀態與控制面板

模擬器可以逐步建立統一的控制面板。

- 行人或乘客相關資訊。
- 可用的操作模式。
- 目前的模擬設定。

控制面板的目標是讓使用者能夠快速理解目前的遊戲狀態。

這樣可以減少介面擁擠的問題，也能讓使用者更容易找到需要的功能。

其中的 `stops` 可以在取得並確認站點資料後，再填入站點名稱或其他站點資訊。

### 6.3 為什麼需要統一路線資料？

如果每條路線都使用不同的程式碼，新增路線時就需要修改許多地方。

當路線數量增加，可能會出現：

- 路線按鈕與實際資料不一致。
- 部分路線無法正常切換。
- 車輛使用錯誤的站點順序。
- 同一段程式碼被重複撰寫。
- 修改一條路線卻影響其他路線。

使用統一資料結構，可以讓路線選擇介面、車輛系統與站點顯示共用同一份資料。

未來若需要加入路線搜尋、收藏、站點資訊或路線比較，也會更加方便。

### 6.4 站點與停靠行為

未來如果要實作更完整的公車模擬，可以為每個站點設定：

- 站點識別碼。
- 站點名稱。
- 所屬路線。
- 站點順序。
- 站點位置。
- 是否允許停靠。
- 上車乘客數。
- 下車乘客數。
- 站點顯示資訊。

車輛到達站點時，可以根據站點資料決定是否停車、停留多久，以及是否需要更新乘客數量。

這樣能建立更清楚的公車運行流程，也方便測試路線是否正確。

### 6.5 真實交通資料與模擬資料

如果未來要使用台中的真實交通資料，可以參考臺中市政府資料開放平台。

官方資料平台提供資料集下載與 API 介接等方式，可作為後續研究交通資訊的入口：

https://opendata.taichung.gov.tw/

資料開發指南：

https://opendata.taichung.gov.tw/develop-guide

使用真實資料時，建議確認資料集的更新時間、欄位定義、授權條款及是否適合目前的模擬用途。

此外，真實公車路線資料與遊戲內的移動資料應該分開處理。即使路線名稱相同，也不代表遊戲中的車速、班距或乘客數量必須完全符合現實。

## 八、遊玩教學

### 8.1 第一次進入遊戲

第一次進入模擬器時，建議先確認網頁是否完整載入。

接著觀察主要畫面，找到方向控制、路線選擇與其他控制圖示。

不需要一次嘗試所有功能，可以先從最基本的操作開始，再逐步探索其他按鈕。

如果畫面沒有顯示預期內容，請先確認網路連線與瀏覽器是否支援目前使用的網頁功能。

### 8.2 選擇公車路線

在具有路線選項的版本中，可以查看畫面上的路線按鈕。

例如，部分版本可見：

- 920
- 921
- 66
- 21 繞 1

選擇路線時，應觀察畫面是否有路線狀態、車輛或其他提示發生變化。

如果按下按鈕後沒有明顯反應，建議確認：

1. 該按鈕是否有對應的事件處理程式。
2. 路線資料是否已經載入。
3. 瀏覽器開發者工具是否出現 JavaScript 錯誤。
4. 是否有其他控制狀態阻止操作。
5. 目前使用的版本是否真的支援該項功能。

### 8.3 使用方向控制

方向控制可以作為基本操作的起點。

建議先單獨測試每個方向按鈕，再觀察多個方向操作是否會互相影響。

如果未來加入鍵盤控制，可以考慮提供以下設定：

- 使用方向鍵操作。
- 使用 WASD 操作。
- 使用畫面按鈕操作。
- 自訂快捷鍵。
- 切換控制方式。

這些鍵盤配置屬於建議功能，是否支援應以實際版本為準。

### 8.4 使用暫停控制

如果版本中的暫停按鈕已經實作，可以用它來暫停或恢復模擬。

良好的暫停機制應該能夠停止主要模擬更新，而不只是改變按鈕外觀。

如果未來包含車輛、行人與動畫，建議統一管理模擬狀態，避免暫停後仍有部分物件繼續移動。

### 8.5 探索其他功能

完成基本操作後，可以繼續查看廣播、機器人、行人、捷運與其他介面。

如果某項功能尚未完成，可以將它視為測試項目，記錄實際行為並回報問題。

透過這種方式，使用者也能協助開發者發現操作上的問題。

### 8.6 建議的測試流程

如果你希望完整測試某個版本，可以按照以下順序進行：

1. 開啟網頁。
2. 確認畫面與控制介面是否正常顯示。
3. 測試每個方向按鈕。
4. 測試暫停與恢復操作。
5. 測試所有可見路線選項。
6. 檢查其他控制圖示。
7. 重新整理頁面，確認載入是否正常。
8. 測試瀏覽器縮放與視窗大小變化。
9. 檢查是否有錯誤訊息。
10. 記錄成功與失敗的操作。

這份流程可以作為後續版本測試的基礎。

## 九、帳號與登入介面

部分版本的頁面中可以看到 Google、Facebook、電子郵件與密碼相關的登入介面。

### 9.1 登入功能的可能用途

如果未來要完整實作帳號系統，可以考慮讓使用者：

正式實作時，應確認：

- 應用程式的身分設定。
- 授權回呼網址。
- 網域與來源限制。
- 登入狀態管理。
- 登出流程。

不要將密碼直接以明文保存，也不要將私人 API 金鑰、管理員密碼或其他機密資訊放進公開的 HTML 或 JavaScript 原始碼。

GitHub Pages 主要負責提供靜態網頁，若需要真正的帳號驗證與雲端資料保存，通常還需要搭配適當的後端服務。

### 9.4 登入功能的驗收標準

未來可以使用以下項目確認登入系統是否完成：

- 使用者能否成功登入。
- 錯誤帳號是否會得到合理提示。
- 使用者能否正常登出。
- 重新整理後登入狀態是否符合預期。
- 不同帳號之間的資料是否正確隔離。
- 未登入使用者是否無法讀取不應公開的資料。
- 私人金鑰是否安全保存。
- 帳號資料是否能依照設計正確保存與刪除。

## 十、網頁技術與專案架構

### 10.1 專案目前的公開形式

## 十二、開發與維護指南

### 12.1 開發前的準備

修改程式碼之前，建議先確認：

- 目前正在修改哪個版本。
- 該版本是否為正式版或測試版。
- 是否有其他版本共用相同資源。
- 修改是否會影響路線切換。
- 是否會改變現有的控制方式。
- 是否涉及帳號或外部服務。
- 是否需要調整 README 文件。

如果只想測試新的功能，建議先在 Beta 版本中進行，不要直接修改正式版而未經測試。

### 12.2 功能開發流程

每次新增功能時，可以採用以下流程：

1. 定義功能目的。
2. 確認操作介面。
3. 設計資料結構。
4. 撰寫功能程式碼。
5. 測試基本情況。
6. 測試錯誤情況。
7. 檢查效能。
8. 檢查不同瀏覽器的行為。
9. 更新文件。
10. 發布測試版本。

這樣可以降低一次加入太多功能所造成的問題。

### 12.3 版本測試

每次更新後，建議至少確認以下項目：

| 測試項目 | 驗收方向 |
|---|---|
| 網頁載入 | 頁面能否正常開啟 |
| 畫面顯示 | 控制介面是否完整 |
| 按鈕操作 | 點擊後是否符合預期 |
| 路線選擇 | 路線切換是否正常 |
| 模擬狀態 | 暫停與恢復是否一致 |
| 鍵盤操作 | 若有實作，確認快捷鍵行為 |
| 瀏覽器相容性 | 常見瀏覽器是否正常 |
| 音效與廣播 | 若有實作，確認播放與關閉 |
| 帳號功能 | 若有實作，測試登入與登出 |
| 效能 | 是否出現明顯卡頓 |
| 錯誤處理 | 錯誤時是否有合理提示 |

### 12.4 效能最佳化

如果未來加入大量車輛、行人或交通事件，應特別注意效能。

可以考慮以下方向：

- 避免不必要的 DOM 更新。
- 將靜態內容與動態內容分開。
- 避免重複建立相同物件。
- 控制動畫更新頻率。
- 減少不必要的計算。
- 對遠離主要視野的物件降低更新頻率。
- 只在必要時更新資訊面板。
- 使用瀏覽器開發者工具分析效能。
- 在不同效能的電腦上進行測試。

如果採用 Canvas 或其他繪圖技術，也應針對實際場景測試，而不是只根據理論判斷效能。

### 12.5 使用者介面改善

隨著功能增加，介面也需要持續改善。

未來可以考慮：

- 更清楚的按鈕名稱。
- 滑鼠懸停提示。
- 操作成功與失敗提示。
- 更容易辨認的選單。
- 可收合的設定面板。
- 桌面與手機版排版。
- 字體大小調整。
- 高對比顯示。
- 鍵盤操作支援。
- 減少不必要的動畫。

無障礙設計不只是增加一個圖示，而是要確保使用者能夠理解介面、操作控制項目，並取得重要資訊。

### 14.3 常見技術問題

#### 網頁無法開啟

請確認網址是否正確，以及網路連線是否正常。

如果只有特定版本無法開啟，可以嘗試其他版本，並記錄發生問題的網址。

#### 網頁可以開啟，但部分內容沒有顯示

可能的原因包括：

- JavaScript 發生錯誤。
- 外部資源無法載入。
- CSS 路徑錯誤。
- 圖片或其他素材不存在。
- 瀏覽器快取仍保留舊版內容。

可以先重新整理頁面，再透過瀏覽器開發者工具查看錯誤。

#### 按鈕沒有反應

請確認：

- 按鈕是否已經綁定事件。
- 事件處理函式是否正確。
- 是否發生 JavaScript 錯誤。
- 是否有其他透明元素擋住按鈕。
- 是否有模擬狀態限制操作。
- 是否有外部服務未完成載入。

#### 路線切換沒有反應

請檢查：

- 路線按鈕是否對應正確的路線識別碼。
- 路線資料是否存在。
- 切換事件是否成功觸發。
- 畫面是否有更新。
- 是否存在拼字或大小寫不一致。

#### 更新後仍然看到舊畫面

GitHub Pages 與瀏覽器可能需要時間更新快取。

可以嘗試重新整理頁面，或使用瀏覽器的強制重新載入功能。

如果問題持續發生，請確認 GitHub 上的檔案是否已經更新，以及網站是否已成功發布。

## 十七、常見問題 FAQ

### Q1：台中城市模擬器需要下載嗎？

正式版是以正式體驗為定位的入口，Beta 版本則適合測試與觀察不同階段的變更。

不過，具體功能差異仍應以每個版本的程式碼與實際執行結果為準。

### Q5：這些路線是否完全按照真實台中公車運作？

不能僅根據路線名稱判定。

可以嘗試使用支援現代網頁標準的手機瀏覽器開啟。

### Q7：為什麼某個按鈕沒有反應？

可能是該功能尚未實作、事件處理程式發生錯誤，或是目前的操作狀態不允許執行。

### Q8：Google 或 Facebook 登入可以使用嗎？

### Q9：遊戲進度會自動保存嗎？

目前不能只根據頁面介面確認進度保存機制是否完整存在。

### Q10：可以新增自己的公車路線嗎？

如果你熟悉 HTML 與 JavaScript，可以研究現有路線按鈕與相關程式碼。

## 十八、使用規範與注意事項

### 18.1 專案定位

台中城市模擬器是一個以台中城市與交通為靈感的網頁模擬專案。

專案中的模擬內容不應直接視為官方交通資訊，也不應將遊戲中的交通行為當作真實道路上的駕駛指引。

如果需要查詢真實的交通資訊，請以相關官方單位發布的資訊為準。

### 18.2 資料正確性

如果未來使用真實地圖、公車路線、站點或其他公共資料，應盡可能記錄：

- 資料來源。
- 資料集名稱。
- 取得日期。
- 更新日期。
- 授權條款。
- 必要的來源標示。

如果模擬資料與真實資料不同，也應避免讓使用者誤以為兩者完全一致。

### 18.3 隱私與帳號

如果未來加入帳號或雲端保存功能，應清楚說明資料用途與保存方式。

不應在公開原始碼中放入私人金鑰、密碼或其他機密資料。

### 18.4 第三方素材

如果使用第三方圖片、音效、字型、圖示或程式碼，應確認使用條件與授權。

不要因為素材可以在網路上找到，就假設它可以不受限制地使用。

### 18.5 授權聲明

本 README 不代表整個專案已經採用特定的開源授權。

在確認 GitHub 儲存庫的授權之前，請不要假設本專案允許任意複製、修改、重新發布或商業使用。

如果希望開放其他人共同開發，建議由專案維護者選擇適合的授權，並在儲存庫根目錄加入相應的 `LICENSE` 檔案。

## 十九、版本管理原則

為了讓專案持續成長，建議未來採用一致的版本管理方式。

### 19.1 版本命名

可以繼續使用清楚的版本名稱，例如：

- Beta V1.0.2
- Beta V1.1.0
- Formal V1.1
- Formal V2.0

這些名稱只是未來可以使用的命名範例，不代表相關版本已經發布。



### 19.4 正式版與測試版的管理

建議正式版以穩定性為主要目標，Beta 版本則用於驗證新功能。

如果某項功能在 Beta 版本中測試成功，可以再決定是否整合到正式版。

若測試版本發生問題，也可以先保留正式版作為可供使用者比較的參考。

這種方式可以減少開發過程中的變更對使用者造成的影響。
